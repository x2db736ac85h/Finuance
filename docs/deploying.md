# Deploying

Two ways to run Finuance: Docker Compose on one host, or Kubernetes with Helm, CloudNativePG and Argo CD. Day-to-day operations (backups, restores, rollbacks, playbooks) are in the [runbook](RUNBOOK.md).

**Docker Compose.** [`deploy/compose/compose.prod.yaml`](../deploy/compose/compose.prod.yaml) runs the released images (`ghcr.io/x2db736ac85h/finuance-api` and `finuance-web`, amd64 and arm64, signed with cosign). It needs only itself and a `.env` ([`.env.prod.example`](../deploy/compose/.env.prod.example), attached to every [release](https://github.com/x2db736ac85h/Finuance/releases) as `finuance.env.example`). Only the web container is published, on `127.0.0.1:8000` by default; the database, the API and the admin ports stay on the internal Compose network.

- Put a reverse proxy with TLS in front of port 8000 (Caddy, Traefik, nginx) and set `FINUANCE_PUBLIC_ORIGIN` to its URL. Production mode sends secure cookies only, so the app works over HTTPS, or over plain http on `localhost` (e.g. through an ssh tunnel to a server).
- **That proxy must pass the client's address** in `X-Forwarded-For`, added by itself: Caddy and Traefik do; nginx needs `proxy_set_header X-Forwarded-For $remote_addr;` (or `$proxy_add_x_forwarded_for`). The API believes only the right-most address that is not one of its own proxies (`FINUANCE_TRUSTED_PROXIES`, by default the Compose network), so a header a visitor sends is ignored. A proxy that passes no address makes every visitor look like one: one person's failed sign-ins would then use up everybody's limit. The API logs a warning the first time it sees that. Keep other containers off the Compose network: each of them could name any client address.
- Sign-up is off by default. Create accounts with the admin CLI: `docker compose … exec -T api /finuance admin create-user --email you@example.com --password-stdin` (it reads the password from standard input), or set `FINUANCE_ALLOW_SIGNUP=true`.
- Demo mode (`FINUANCE_DEMO_MODE=true`): visitors start their own throwaway demo user from the sign-in page ("Try the demo"), deleted with its data after 24 hours. Sign-up is off, uploads are limited to 2 MiB, the migration from the single-file app is refused, at most 5 demo users start per hour and address, and the assistant stays off unless `FINUANCE_DEMO_ASSISTANT=true` (then 10 questions per visitor). `make test-e2e-demo` runs it with [`compose.demo.yaml`](../deploy/compose/compose.demo.yaml).
- Verify an image before you run it (both commands appear with the exact digests in every [release](https://github.com/x2db736ac85h/Finuance/releases)'s notes; [SECURITY.md](../SECURITY.md) explains them). The signature, made by the release workflow for a version tag and nothing else:

  ```sh
  cosign verify ghcr.io/x2db736ac85h/finuance-api:<version> \
    --certificate-identity-regexp '^https://github\.com/x2db736ac85h/Finuance/\.github/workflows/release\.yml@refs/tags/v[0-9]' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com
  ```

  The build provenance (from `v0.4.2`), which says which commit and workflow built it:

  ```sh
  gh attestation verify oci://ghcr.io/x2db736ac85h/finuance-api:<version> \
    --repo x2db736ac85h/Finuance --signer-workflow x2db736ac85h/Finuance/.github/workflows/release.yml
  ```
- Back up the database volume regularly. It holds your original CSV files too.

**Kubernetes with Helm, CloudNativePG and Argo CD** (rehearsed weekly in CI on a kind cluster, including a backup restore and pod kills; running on a reference environment, single-node k3s with a small NVIDIA GPU, since Phase 18):
- The app chart [`deploy/helm/finuance`](../deploy/helm/finuance) runs the api (with an HPA), the worker, the web front end, a migrations Job before every upgrade, and NetworkPolicies.
- The database chart [`deploy/k8s/db`](../deploy/k8s/db) runs a CloudNativePG cluster, with WAL archiving and daily backups to S3-compatible storage.
- [`deploy/k8s/argocd`](../deploy/k8s/argocd) is an Argo CD app-of-apps with Sealed Secrets.
- A release opens a pull request that writes its version and the digests of its two images into [`deploy/environments/homelab`](../deploy/environments/homelab), and merging it deploys. With `image.digests.api` and `image.digests.web` set, the chart runs `name@sha256:…` and a tag that moves can't change what runs; without them it deploys by tag.
- The chart's NetworkPolicies are part of its security, not an extra: the default deny covers every pod of the namespace (`networkPolicy.namespaceWide`), only the ingress controller and the web pods reach the api, only the api, the worker and the migration job reach the database, and only Prometheus's pods reach the metrics port (which has no sign-in and must never be exposed). `trustedProxies` may be a range for that reason only; with the policies off the chart refuses a range. Use `database.sslmode: verify-full` with `database.caSecret` (CloudNativePG: `<cluster>-ca`) so that the app checks who answers as the database.
- **If the internet can reach the instance, switch on the limits at the ingress**: `ingress.limits.enabled: true` adds Traefik middlewares that count per client address in front of every replica: a strict limit for `/api/v1/auth/` (20 a minute by default), a generous one for everything else (50 a second, bursts of 200) and a cap on requests in flight (50). A client over a limit gets `429` from Traefik. The application's own limiters stay, but they count per replica and in memory. Behind one shared address (a company network, a tunnel) every user counts as one client, so they are off by default; with a proxy in front of Traefik set `ingress.limits.forwardedDepth` to the number of trusted proxies. Signatures at admission: [RUNBOOK](RUNBOOK.md), "Image signatures".
- **A cluster without Traefik** (a cloud's own gateway controller, for example Google Kubernetes Engine's): set `ingress.enabled: false` and `gateway.enabled: true` with the host and the Gateway to attach to (`gateway.parentRef`). The chart then renders one Gateway API `HTTPRoute` for `/api/` and `/` with the HSTS header as a route filter, and nothing Traefik-specific. The Gateway itself (address, listener, certificate) is the platform's. Where a load balancer reaches the pods directly, name its address ranges in `networkPolicy.frontDoorCIDRs` and set `networkPolicy.ingressController: null`. Limits per client address are then the gateway's or the cloud's; `ingress.limits` are Traefik middlewares. `gateway.gke.enabled` adds Google's health check and backend policies. An example: [`deploy/environments/gke-lab`](../deploy/environments/gke-lab) (prepared, not yet run on a real cluster).
- [`deploy/k8s/observability`](../deploy/k8s/observability) holds six Grafana dashboards and the alert rules as code: SLO burn rates ([docs/SLO.md](SLO.md)), failing jobs and imports, PostgreSQL, WAL archiving and backup age, failures at the ingress, with an e-mail receiver. The homelab runs it with kube-prometheus-stack and Tempo, all through Argo CD.
- Single-node k3s step by step (Tailscale certificates, an in-cluster backup bucket, the model server on the host, the per-machine values in a private repository, an image admission policy): [RUNBOOK](RUNBOOK.md#bootstrap-on-single-node-k3s). Measured there: restore in 71 s (RPO 96 s), no failed request while pods are killed, the latency SLO held up to about 77 table requests per second, an OpenVAS scan with nothing above "Log" ([docs/perf.md](perf.md), [docs/security-scan.md](security-scan.md)).

Operating it: [docs/RUNBOOK.md](RUNBOOK.md).
